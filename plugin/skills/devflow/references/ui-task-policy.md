# UI task policy — direct invocation and router

Apply this policy before a component's longer playbook, whether called directly or through the lifecycle/portable router. It scopes the bundled UI instructions, including later mandatory house-style, research, draw, image and full-screen reading steps. User/host instructions remain authoritative. Keep the bundle together so every entry resolves this same file.

## Choose the smallest complete route

| Task | Route |
|---|---|
| Small fix to an existing component, state or interaction | Focused route below. An admin screen alone does not trigger the full app workflow. |
| New screen within an accepted system | Reuse its brand, stack and components; load only the screen/platform guidance needed. Draw or a new target is optional if the direction is already accepted. |
| New visual direction or authorized redesign | Full relevant app/site workflow, one design record and necessary research/targets. |
| Review/audit | Inspect and report; change code only if fixes are authorized. Scale evidence to the requested review. |

If a narrow fix reveals a blocking shared defect, explain the dependency and make the necessary complete correction within authorized scope. Do not expand into unrelated styling. Record optional improvements separately.

## Focused route

1. Inspect the affected component, its callers/state, existing tokens, stack and relevant acceptance criteria. Use existing decisions; ask only for missing information that blocks the requested behavior.
2. Keep the accepted brand, layout, typography, dependencies and framework. Load only relevant component guidance. For UI/UX Pro Max, use a targeted UX/stack query if useful; do not generate a replacement design system.
3. Implement the requested correction and necessary connected state changes. Skip full app/site chapters, direction draws, image generation and whole-product redesign for this route. If a specific reference is needed, read only that section. Do not load all four long playbooks just because four UI components are bundled. If all four are explicitly requested, use their relevant roles within this same scope.
4. Verify the affected interaction and error/recovery states, keyboard focus/accessibility and relevant viewport(s). Reuse the project's existing targeted test command; run broader checks when shared behavior is affected. Inspect the actual rendered result when tools permit. Missing browser/native tools leave those checks pending, not passed. Hash receipts and style lint do not prove visual or functional acceptance.
5. Report what changed, checks actually run and unresolved limitations. Reuse one concise task/evidence record; do not create lifecycle gates or ask for already-given approval.

## One accepted direction

Product requirements, accessibility, working behavior and the accepted brand/stack outrank aesthetic defaults in every bundled component. A deliberate purple sidebar, floating label or branded control is not permission to restyle the application. Fix actual contrast, labels or focus defects while preserving identity where possible; explain unavoidable conflicts with the requested behavior.

Frontend Design supplies coherent visual implementation; UI/UX Pro Max supplies relevant interaction/stack guidance; Leonxlnx Taste critiques composition; Uizze UI Taste supplies relevant platform/craft and rendered-evidence guidance. These roles share one decision, not four competing themes.

Treat aesthetic lint findings that conflict with accepted design as advisory and record the reason. Keep them distinct from functional failures. Do not change brand just to reach zero style findings; do not waive real accessibility or behavior defects as branding. Optional image/MCP tools are not prerequisites for a small fix.

Resolve each component's resource paths from its actual skill directory, not the project cwd or another personal installation. For full UI work use [UI coordination](ui-workflow.md); for relevant state checks use [UI acceptance](ui-acceptance.md).
